## Decisions I made (flagged to Mike, not yet confirmed)

Mike was asked these on 2026-10-29 and moved on to "build it with
subagents"; these are the recommended answers, adopted so work can start.
Each is cheap to change until G18c (the designer) ships.

- **Letters plus a `key` field, not Nashville numbers.** The design note
  leaned numbers; once the chart became a file people hand-edit beside the
  lyric chart, letters won: same spelling as the `.pro`, the Key pill already
  transposes letters, and numbers are computed whenever charts are compared.
- **`works/<song root>/chord-chart.yaml`**, YAML with one text line per chart
  line (`| A \ | C#7 \ |`).
- **One parser, in Python.** The build publishes JSON
  (`docs/data/charts/<work-id>.json`), so the browser never parses the
  notation. The designer (G18c) will submit JSON and `process_pending.py`
  will write the YAML.
- **Step 1 notation is chords, `\`, a one-cell meter change, sections,
  repeat counts and form.** Split slots, push, stop / let ring / rest, and
  1st/2nd endings are G18g, after the basics render.
- **One chart per song, only on a song root** (a work with no `song:`).
- **An invalid chart fails the build**, like the tab provenance gate, and a
  pytest sweep catches it in CI before deploy.
- **No real song charts are written by an agent.** Fixtures are Old Home
  Place from the design note (drawn with Mike) and synthetic shapes with
  placeholder chords. Real charts come from people.

## G18a spec: the chart part

### In `work.yaml`

```yaml
- type: chord-chart
  format: chart
  file: chord-chart.yaml
  provenance: {source: ..., submitted_by: ...}
```

At most one `chord-chart` part per work, and only on a song root (a work
whose `work.yaml` has no `song:` field). Anything else is an error.

### The file

Old Home Place, in A to match `works/old-home-place` (bars from the design
note):

```yaml
key: A
meter: duple
drawn_from: lead-sheet.pro
sections:
  Verse: |
    | A \ | C#7 \ | D \ | A \ |
    | \ \ | \ \ | E \ | \ \ |
    | A \ | C#7 \ | D \ | A \ |
    | \ \ | E \ | A \ | \ \ |
  Chorus: |
    | E \ | \ \ | A \ | \ \ |
    | B7 \ | \ \ | E \ | \ \ |
    | A \ | C#7 \ | D \ | A \ |
    | \ \ | E \ | A \ | \ \ |
form: [Verse, Verse, Chorus, Verse, Verse, Chorus, Chorus]
```

Top-level fields (any other key is an error, so typos don't pass silently):

| Field | Required | Rule |
|---|---|---|
| `key` | yes | a key the index build knows (`KEYS` in `scripts/lib/build_index.py`) |
| `meter` | no, default `duple` | `duple`, `3/4` or `6/8`. Slots per cell: duple 2, 3/4 1, 6/8 2 |
| `drawn_from` | no | the `file` of a `lead-sheet` part of the same work |
| `sections` | yes | non-empty ordered mapping, section name → chart lines (a YAML block string) |
| `repeats` | no | mapping, section name → integer ≥ 1 (default 1) |
| `form` | no | list of section names; each must exist in `sections` |

### Chart lines

- Blank lines are skipped. Every other line starts and ends with `|`
  (surrounding whitespace allowed); `|` separates cells; a line holds at
  least one cell.
- A cell is an optional meter override as its first token, then its slot
  tokens separated by whitespace. Overrides: `2/4` (1 slot), `3/4` (1 slot),
  `4/4` (2 slots), allowed only when the chart's meter is `duple` or `3/4`.
- A cell holds exactly the slot count of its meter (the override's, else
  the chart's). A wrong count is an error naming section, line and cell.
- A slot is `\` (keep playing) or a chord. Chord validity is the book's rule:
  port `isValidChord` (and its `CHORD_QUALITY_RE`) from `docs/js/chords.js`
  to Python, and pin both with one shared table,
  `tests/fixtures/chord-chart/chord-tokens.json` (valid and invalid tokens),
  read by a pytest and a Vitest test. Precedent for a shared table:
  `supabase/functions/_shared/testdata/ownership-cases.json`.
- The first slot of every section is a chord, not `\`.
- Parsing reports every error with its location, not just the first.

### Python module: `scripts/lib/chord_chart.py`

- Parse text into a chart, with all errors collected.
- Validate against its work (`drawn_from` names a lead-sheet part).
- Serialize a chart to canonical YAML text (single spaces inside lines:
  `| A \ | C#7 \ |`). `parse(serialize(c)) == c`, and serializing twice is
  byte-identical. G18c's server-side write will use this.
- Convert to the published JSON:

```json
{
  "key": "A",
  "meter": "duple",
  "drawn_from": "lead-sheet.pro",
  "sections": [
    {"name": "Verse", "repeat": 1,
     "lines": [[{"slots": ["A", null]}, {"slots": ["C#7", null]}, {"slots": ["D", null]}, {"slots": ["A", null]}]]}
  ],
  "form": ["Verse", "Verse", "Chorus"]
}
```

`null` is a hold. A cell with an override carries `"meter": "2/4"`.
`drawn_from` and `form` are omitted when absent.

### `docs/js/chord-chart.js` (pure: no DOM, no fetch)

Works on the published chart JSON (G18a shape) and the lyric chart's sections
as `parseChordPro()` (`docs/js/renderers/chordpro.js`) returns them.

- **Musical sections** of a lyric chart: the parsed sections that carry lyric
  or chord lines (not comments, ABC, tab or grid blocks). These are what line
  up with the chart's `form`.
- **`alignForm(chart, lyricSections)`**: pair each musical lyric section with
  the chart section its `form` entry names, in order. Aligned only when the
  counts are equal; otherwise say so (the UI shows chart view only, plus a
  one-line note).
- **Line chords:** a line's chords in order, consecutive repeats collapsed,
  then a leading chord dropped when it equals the chord already sounding at
  the end of the previous line. The same rule on both sides. For a chart line,
  holds (`null`) are skipped.
- **`compareSections(...)`**: when a chart section and its lyric section have
  the same number of lines, compare line by line; otherwise compare the
  section's whole chord sequence. Compare key-relatively (semitones from each
  side's own key: the chart's `key`, the lyric chart's detected or declared
  key), so the Key pill can never create a mismatch. Return each mismatch
  with its lyric section, line, and both chord lists in the lyric chart's
  spelling.
- **`regroupBars(section, cellsPerBar)`**: 1 or 2 cells a bar. Pairing restarts
  at each chart line; an odd cell at the end of a line is a half bar.
- **`carriedChords(section)`**: the chord sounding at the start of each line
  (for the faint chord in a line's first slot when it is a hold).
- **`transposeChart(chart, semitones)`** using `transposeChord` from
  `docs/js/chords.js`; the key moves too.
- **`practiceOrder(chart, alignment)`**: the unrolled list of chart sections:
  the aligned lyric order when there is one, else `form`, else each section
  `repeat` times in order.

## G18b2 spec: the chart on the song page

Build what Mike approved in `design/ui-states/proposed/g18b-chart-desktop.html`

### Where it shows

- Only on a work whose index row has `chord_chart` (versions: later). Fetch
  that JSON lazily alongside the lead sheet; the service worker already
  caches `data/**.json`.
- **Wide screens:** the lead-sheet part becomes two columns, lyrics left and
  chart right, as in the desktop mockup. No Chart tab.
- **Narrow screens:** a `Chart` part tab beside the lead sheet's tab (the
  existing `renderPartTabs` / `selectPart` path; the lead sheet's tab reads
  `Lyrics`). Pick the breakpoint the way the song page already does.
- Everything goes through `openWork`; no new page or route
  (`docs/js/CLAUDE.md`, "Routing" and "Navigation invariants").

### What it draws

- **Chart view:** each section once, captioned with how many times it is sung
  ("sung 4 times") when aligned, else its repeat count. The chart column is
  sticky beside the lyrics on wide screens. Form line and legend as drawn;
  "Chart by Mike Beaumier" from the JSON's `by`.
- **Practice mode:** the practice order (`practiceOrder`). Wide: each lyric
  section beside its chart section, row by row (chart line level with its
  lyric line when the counts match). Narrow: each chart line under its lyric
  line when the counts match, else the chart section under its lyric section.
  **No playback yet**: no transport and no "playing" highlight (G18d adds
  both, with the bass).
- **Toggles** in the chart header: `Chart | Practice` (per page load, default
  Chart) and `Bars: One cell | Two cells` (remembered per device in
  localStorage).
- **Cells:** equal sub-cells per slot, chord or `\` centered; holds faint; the
  carried chord faint in a line's first slot; dashed line between the cells of
  a two-cell bar; a half bar where `regroupBars` says so. Chords through
  `chordGlyphHtml()` (`docs/js/chords.js`), never raw text.
- **Key pill:** the chart follows the lyric chart's key (`transposeChart` by
  the semitones between the chart's `key` and the displayed key), redrawn by
  the same key subscription the lyrics use (respect the `renderedKey` guard).
  Nashville mode shows numbers in the chart as it does in the lyrics.
- **Mismatches** (`compareSections`, with the lyric chart's declared key):
  under the lyric line, a quiet note "Differs from the chart: X there, Y here"
  (chords as glyphs). A section-level mismatch puts the note under the
  section label. When the form doesn't line up (`alignForm` says `count`),
  one quiet line in the chart column says so and practice mode follows the
  chart's own form.
