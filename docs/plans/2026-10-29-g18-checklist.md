## Decisions (Mike, 2026-10-28 and 29)

The list is in the design note ("Decisions"). In short: a slot is one bass
note, a cell is boom-chuck boom-chuck (one slot in 3/4), cells are stored and
barring is a display toggle, the chart is its own part on the song's root
work, people draw charts, breaks belong to set lists, bass → guitar →
mandolin, no banjo. Mike asked on 2026-10-29 for this to be built by
subagents with Claude orchestrating and validating.

## Decisions I made (flagged to Mike, not yet confirmed)

Mike was asked these on 2026-10-29 and moved on to "build it with
subagents"; these are the recommended answers, adopted so work can start.
Each is cheap to change until G18c (the designer) ships.

- **Letters plus a `key` field, not Nashville numbers.** The design note
  leaned numbers; once the chart became a file people hand-edit beside the
  lyric chart, letters won: same spelling as the `.pro`, the Key pill already
  transposes letters, and numbers are computed whenever charts are compared.
- **`works/<song root>/chord-chart.yaml`**, YAML with one text line per chart
  line (`| A \ | C#7 \ |`).
- **One parser, in Python.** The build publishes JSON
  (`docs/data/charts/<work-id>.json`), so the browser never parses the
  notation. The designer (G18c) will submit JSON and `process_pending.py`
  will write the YAML.
- **Step 1 notation is chords, `\`, a one-cell meter change, sections,
  repeat counts and form.** Split slots, push, stop / let ring / rest, and
  1st/2nd endings are G18g, after the basics render.
- **One chart per song, only on a song root** (a work with no `song:`).
- **An invalid chart fails the build**, like the tab provenance gate, and a
  pytest sweep catches it in CI before deploy.
- **No real song charts are written by an agent.** Fixtures are Old Home
  Place from the design note (drawn with Mike) and synthetic shapes with
  placeholder chords. Real charts come from people.

## G18a spec: the chart part

### In `work.yaml`

```yaml
- type: chord-chart
  format: chart
  file: chord-chart.yaml
  provenance: {source: ..., submitted_by: ...}
```

At most one `chord-chart` part per work, and only on a song root (a work
whose `work.yaml` has no `song:` field). Anything else is an error.

### The file

Old Home Place, in A to match `works/old-home-place` (bars from the design
note):

```yaml
key: A
meter: duple
drawn_from: lead-sheet.pro
sections:
  Verse: |
    | A \ | C#7 \ | D \ | A \ |
    | \ \ | \ \ | E \ | \ \ |
    | A \ | C#7 \ | D \ | A \ |
    | \ \ | E \ | A \ | \ \ |
  Chorus: |
    | E \ | \ \ | A \ | \ \ |
    | B7 \ | \ \ | E \ | \ \ |
    | A \ | C#7 \ | D \ | A \ |
    | \ \ | E \ | A \ | \ \ |
form: [Verse, Verse, Chorus, Verse, Verse, Chorus, Chorus]
```

Top-level fields (any other key is an error, so typos don't pass silently):

| Field | Required | Rule |
|---|---|---|
| `key` | yes | a key the index build knows (`KEYS` in `scripts/lib/build_index.py`) |
| `meter` | no, default `duple` | `duple`, `3/4` or `6/8`. Slots per cell: duple 2, 3/4 1, 6/8 2 |
| `drawn_from` | no | the `file` of a `lead-sheet` part of the same work |
| `sections` | yes | non-empty ordered mapping, section name → chart lines (a YAML block string) |
| `repeats` | no | mapping, section name → integer ≥ 1 (default 1) |
| `form` | no | list of section names; each must exist in `sections` |

### Chart lines

- Blank lines are skipped. Every other line starts and ends with `|`
  (surrounding whitespace allowed); `|` separates cells; a line holds at
  least one cell.
- A cell is an optional meter override as its first token, then its slot
  tokens separated by whitespace. Overrides: `2/4` (1 slot), `3/4` (1 slot),
  `4/4` (2 slots), allowed only when the chart's meter is `duple` or `3/4`.
- A cell holds exactly the slot count of its meter (the override's, else
  the chart's). A wrong count is an error naming section, line and cell.
- A slot is `\` (keep playing) or a chord. Chord validity is the book's rule:
  port `isValidChord` (and its `CHORD_QUALITY_RE`) from `docs/js/chords.js`
  to Python, and pin both with one shared table,
  `tests/fixtures/chord-chart/chord-tokens.json` (valid and invalid tokens),
  read by a pytest and a Vitest test. Precedent for a shared table:
  `supabase/functions/_shared/testdata/ownership-cases.json`.
- The first slot of every section is a chord, not `\`.
- Parsing reports every error with its location, not just the first.

### Python module: `scripts/lib/chord_chart.py`

- Parse text into a chart, with all errors collected.
- Validate against its work (`drawn_from` names a lead-sheet part).
- Serialize a chart to canonical YAML text (single spaces inside lines:
  `| A \ | C#7 \ |`). `parse(serialize(c)) == c`, and serializing twice is
  byte-identical. G18c's server-side write will use this.
- Convert to the published JSON:

```json
{
  "key": "A",
  "meter": "duple",
  "drawn_from": "lead-sheet.pro",
  "sections": [
    {"name": "Verse", "repeat": 1,
     "lines": [[{"slots": ["A", null]}, {"slots": ["C#7", null]}, {"slots": ["D", null]}, {"slots": ["A", null]}]]}
  ],
  "form": ["Verse", "Verse", "Chorus"]
}
```

`null` is a hold. A cell with an override carries `"meter": "2/4"`.
`drawn_from` and `form` are omitted when absent.

### Build (`scripts/lib/build_works_index.py`)

- Validate each `chord-chart` part with `chord_chart.py`. Any invalid chart,
  a second chart on one work, or a chart on a version: print an ERROR list
  (work, file, messages) and exit 1 before writing anything, like the tab
  provenance gate.
- Publish each valid chart to `docs/data/charts/<work-id>.json` and set
  `chord_chart: "data/charts/<work-id>.json"` on that work's index row.
- Prune `docs/data/charts/*.json` files no row references (every file there
  is generated). Add `docs/data/charts/` to `.gitignore`.
- A chart alone doesn't make a work publishable (it still needs a lead
  sheet, tab, document, or placeholder status).
- `scripts/lib/work_schema.py`: add `chord-chart` where part types are
  listed. `works_writer.py` is untouched (G18c).
